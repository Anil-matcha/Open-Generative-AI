# Plan: Integrate 4 External Apps as Standalone Iframes (Superpowers Methodology)

## Context & Git Audit

- The Higgsfield monorepo previously included four third-party apps (Open-Pomelli, Vibe-Workflow, videco_ai_platform, ai-headshot-generator) as git submodules.
- They were removed because they caused deployment failures on Netlify (see DEPLOYMENT_SUMMARY.md).
- **Git commit audit**:
  - `5f8bd424` merged branch `codex/integrate-open-pomelli-as-ai-marketing-studio` — integrated Open-Pomelli as native pages (MarketingStudioPage, BrandDNAExtractor, etc.). Those were later removed entirely.
  - `abfcd2ce` referenced submodule clone instructions.
  - `3c3ed191` and subsequent commits cleaned all submodule entries from `.gitmodules`.
  - No current traces of the four apps remain in the working tree; only residual imports exist (e.g., `WorkflowEmbedPage.js` expects `VITE_WORKFLOW_APP_URL`, `BrandDNAExtractor.js` mentions Open-Pomelli).
- Goal: Reintroduce these apps as **standalone iframe-embedded applications** matching the pattern of `apps/remix-go` and `apps/ai-vfx`, ensuring Netlify compatibility and preserving **all features** from the original repositories.

## Repo Analysis (Upstream Source)

We fetched `package.json` and README for each upstream repo (deangilmoreremix variants):

| App | Stack | Key Dependencies | Server Requirements |
|-----|-------|------------------|---------------------|
| Open-Pomelli | Next.js 16 (App Router), React 19, TS | Prisma, Playwright, sharp, zod | SQLite/Postgres (Prisma), Playwright (site scraping), MuAPI calls from server routes |
| Vibe-Workflow | Monorepo: Next.js client + FastAPI backend + `workflow-builder` React lib | Next.js, FastAPI, workflow-builder | Python backend (FastAPI) + Node client; MuAPI key |
| videco_ai_platform | Next.js (likely pages router), React 18 | Chakra UI, Cloudinary, FFmpeg.wasm, Stripe, Supabase, Inngest | API routes, webhooks, Stripe, background jobs |
| ai-headshot-generator | Next.js 16, React 19, TS | NextAuth, Prisma, Stripe, Supabase | PostgreSQL (Prisma), NextAuth sessions, Stripe webhooks |

All four are **full-stack apps** requiring server-side components. They cannot be trivially exported to static SPAs without architectural changes.

## Integration Strategies

### Strategy A – Embed as Separate Services (Minimal Rewrite, Full Features)
- Clone each repo into `apps/<slug>` as a workspace (no submodules).
- Keep their original stack intact (Next.js/FastAPI).
- Dev: run each on a fixed port; configure Vite dev server proxy so `http://localhost:8080/apps/<slug>` proxies to the service (same-origin iframe).
- Prod: either (a) deploy each service separately and use Netlify `_redirects` to proxy paths, or (b) build them alongside (only if static-export possible). Preserves 100% features; low code churn.
- Cons: Requires managing multiple services; auth sharing must be handled via forwarded cookies.

### Strategy B – Convert to Vite SPA + Rewrite Backend (Maximum Integration)
- Reimplement each as a Vite+React SPA; move server logic to Higgsfield Edge Functions or new services.
- Full TDD, aligned with monolith. Netlify-friendly single deploy.
- Cons: Massive development effort; risk of missing edge cases; long timeline.

### Strategy C – Hybrid
- UI converted to Vite SPA; backend-heavy features (scraping, video processing) kept as separate services proxied under `/apps/<slug>/api/*`.
- Balanced approach.

## Recommendation

Given that (1) the apps are full-stack, (2) "all features" is required, and (3) prior attempt to merge Open-Pomelli as native pages was later removed, **Strategy A (Separate Services with Proxy)** is strongly recommended:

- Clone repos directly → minimal conversion work.
- Features remain intact, including Playwright scraping, Python backend, Stripe flows, FFmpeg, etc.
- Isolation prevents contaminating main app.
- Can scale/deploy each independently later.

- Build integration with TDD: write Playwright tests first, then wiring code.

## Open Questions

1. **Deployment model**: Should each app be a separate deployment (e.g., Vercel/Railway) with Netlify proxies via `_redirects`, or should they be built/runtime within the same monorepo process? The latter is only feasible for parts that can be statically served.
2. **Auth sharing**: Do users need SSO across all apps? If yes, we must forward Supabase session cookies through the proxy and configure each app to accept the same JWT.
3. **Local dev ports**: Assign each service a fixed port for consistency (suggest: open-pomelli 3000, vibe-workflow-client 3001, vibe-workflow-server 8000, videco 3002, headshot 3003).
4. **Build steps on Netlify**: If separate deployments, main site build remains unchanged; we only need `_redirects` entries. If monolithic, we need to extend `build:all` to build each service and copy static assets where possible.

## High-Level Implementation (Strategy A)

Per-app steps:

1. **Clone**
   ```bash
   git clone https://github.com/deangilmoreremix/Open-Pomelli apps/open-pomelli
   # (sim similarly for others, using correct original repo names)
   ```

2. **Workspace setup**  
   Ensure each `apps/<slug>/package.json` has a unique `"name": "<slug>"`. Run `pnpm install` at root to link workspaces.

3. **Base path & proxy adaptation**
   - **Next.js apps**: add/edit `next.config.js` with:
     ```js
     export default {
       basePath: '/apps/<slug>',
       // For apps that rely on API routes, they will be served under the same base.
     };
     ```
   - **Vite/FastAPI combos** (Vibe-Workflow): configure client base (`vite.config.ts` base: `/apps/<slug>/`) and ensure server mounts at `/apps/<slug` via proxy.
   - Replace any hardcoded `https://api.muapi.ai` with relative `/api/app/` (so requests go through main app's proxy and carry auth).

4. **Development proxy in main Vite**
   Update root `vite.config.js`:
   ```js
   server: {
     port: 8080,
     proxy: {
       '/api': { ...existing... },
       '/apps/open-pomelli': { target: 'http://localhost:3000', changeOrigin: true, ws: true },
       '/apps/vibe-workflow': { target: 'http://localhost:3001', changeOrigin: true, ws: true },
       '/apps/videco-ai-platform': { target: 'http://localhost:3002', changeOrigin: true, ws: true },
       '/apps/ai-headshot-generator': { target: 'http://localhost:3003', changeOrigin: true, ws: true },
       // If Vibe-Workflow has separate backend on 8000, proxy /apps/vibe-workflow/api/* → http://localhost:8000
     }
   }
   ```
   - Add root npm scripts for convenience:
     ```json
     "dev:open-pomelli": "pnpm --filter open-pomelli run dev",
     "dev:vibe-workflow": "pnpm --filter vibe-workflow run dev:app",
     "dev:videco": "pnpm --filter videco-ai-platform run dev",
     "dev:headshot": "pnpm --filter ai-headshot-generator run dev",
     ```

5. **Production routing**
   - **Preferred**: Deploy each app as its own site. Add `_redirects` to main repo:
     ```
     /apps/open-pomelli/*  https://open-pomelli.yourdomain.com/:splat  200
     /apps/vibe-workflow/*  https://vibe-workflow.yourdomain.com/:splat  200
     ...
     ```
   - Configure each app to use the same Supabase project and MuAPI key (via env vars).
   - If any app can be fully static-exported (`next export`), we can instead build it and copy to `public/apps/<slug>/` (update `build:all` scripts).

6. **Router & Sidebar**
   - Create page components (`src/components/OpenPomelliPage.js`, etc.) derived from `RemixGoPage.js`, with:
     - iframe `src` = `/apps/<slug>/` (proxied or static)
     - Loading/error text per app name.
   - Add route entry in `src/lib/router.js`:
     ```js
     'open-pomelli': () => import('../components/OpenPomelliPage.js').then(m => m.OpenPomelliPage()),
     ```
   - Add sidebar nav item (`src/components/Sidebar.js`):
     ```js
     { id: 'open-pomelli', icon: `<svg viewBox="0 0 24 24" fill="none" stroke="currentColor" class="w-5 h-5"><path d="M12 2v20M2 10h20"/></svg>`, label: 'Open Pomelli' },
     ```

7. **Build script updates**
   - For static-capable apps: `"build:open-pomelli": "pnpm --filter open-pomelli run build && mkdir -p public/apps/open-pomelli && cp -r apps/open-pomelli/out public/apps/open-pomelli/"`
   - For Next.js services not included in main build: add a placeholder that logs a warning; `build:all` can skip them.
   - Extend `build:all` accordingly.

8. **Testing**
   - Add e2e tests to `tests/e2e/apps-integration.spec.js` covering navigation, iframe load, network calls.
   - Verify MuAPI proxy calls appear in Network tab, console clean.
   - Test auth flows (login, then access app) if applicable.

9. **Documentation & Deploy**
   - Update `README.md` with per-app run instructions.
   - Document required env vars per app.
   - Create a `NETLIFY_DEPLOY.md` with redirects config if using separate deployments.

## Risks & Mitigations

- **Service sprawl** – Each app adds runtime. Mitigation: Document resource requirements; consider merging backends where feasible later.
- **Auth propagation** – Cookies may not forward automatically. Mitigation: Configure proxy to forward all headers; if needed, modify apps to read session from forwarded header or via postMessage.
- **Build complexity** – Monorepo with mixed frameworks. Mitigation: Keep each app self-contained; root build only cares about copying static artifacts.
